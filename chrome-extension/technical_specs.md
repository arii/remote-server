# LocalForm AI — Technical Spec (as shipped)

This document describes the extension **as it exists today** on
`feat/localform-ai-chrome-extension` (OD-19 structural phase, PRs #1302/#1310/#1311/#1312).
Every file, storage key, and message type named below exists in
`chrome-extension/`. Roadmap items that are **not** built (IndexedDB, TypeScript,
shadow-DOM piercing, permission-scope reduction) live in
[`future_work.md`](./future_work.md) and are out of scope here.

## 1. Architecture — three runtime contexts

All paths relative to `chrome-extension/extension/`.

| Context | Files | Type | Role |
|---|---|---|---|
| **Content script** | `content-script.js` (~730 lines) + `lib/matcher.legacy.js` | classic scripts, injected on `<all_urls>`, `all_frames: true`, `document_idle` | Scans forms, resolves labels, fills fields, captures page snapshots, watches for submissions |
| **Service worker** | `service-worker.js` (~290 lines) | ES module (`"type": "module"` in `manifest.json`) | Owns all vault/delta writes; routes messages; toolbar badge |
| **Side panel** | `sidepanel.js` (~1,500 lines), `sidepanel.html`, `sidepanel.css` | ES module | Vault/delta UI, form fill orchestration, Chrome Built-in AI (LanguageModel, Summarizer) |

Shared pure logic lives in `extension/lib/`:

- `matcher.js` — the one set of label-matching rules (§4).
- `matcher.legacy.js` — the classic-script twin of `matcher.js`, generated by
  `scripts/build.mjs` (`scripts/legacy-matcher.mjs`), attached to
  `window.__LOCALFORM_MATCHER__` for the content script. Do not hand-edit it.
- `storage-mutations.js` — pure vault/delta state transitions plus the
  serialized mutation queue (§3).
- `delta-guards.js` — observer dedupe guards (`normalizeForDedup`,
  `valueAlreadyHeld`).
- `hydration.js` — verified-fill verdicts and summaries (`verifyValueLanded`,
  `summarizeHydrationResult`).
- `vault.js` — `deduplicateVault` merge rules.

The content script cannot `import` ES modules (classic-script injection per
`manifest.json`), so it consumes the matcher exclusively through the
`window.__LOCALFORM_MATCHER__` hook; the side panel and service worker import
`lib/*.js` modules directly.

## 2. Storage — keys and single owners

All persistence is `chrome.storage.local`. Four keys, each with exactly one
writer:

| Key | Writer | Written by |
|---|---|---|
| `userContextVault` | **service worker only** | `handleMutation` for panel mutations; `sanitizeVaultStorage` at install/startup |
| `pendingDeltas` | **service worker only** | `handleMutation` and `enqueueObserverMerge` — both inside the same serialized queue |
| `observerDomainAllowlist` | side panel only (Observer tab toggle, fail-closed read in content script) | single-owner, no contention |
| `activeSessionContext` | side panel only (job-description capture) | single-owner, no contention |

The side panel never writes vault or delta state. It sends typed mutation
messages (§3) and re-renders its vault/delta views after each mutation's
response (the `renderVault()` calls that follow every `sendMessage`), plus on
search input and category-filter changes. A grep-based
regression test (`tests/single-writer.test.js`) fails the suite if any
`chrome.storage.local.set` for `userContextVault`/`pendingDeltas` appears
outside `service-worker.js`.

Vault entries: `{ id, category, key, aliases, value, tags, updatedAt }`. IDs are
canonical (`identity.full_name`) for seeded/manual facts or
`category.timestamp[_n]` for approved deltas; `deduplicateVault` sorts
canonical IDs first so they win merges. Pending deltas:
`{ deltaId, action: "create"|"update", targetEntryId?, category, key, proposedValue, previousValue?, evidenceSnippet, sourceUrl, confidence }`,
capped at 100.

## 3. Message API (side panel / content script → service worker)

The service worker's `chrome.runtime.onMessage` handler dispatches:

**Vault/delta mutations** (each returns `{ ok: true, vaultCount, pendingDeltas }`):

| `type` | Payload | Effect |
|---|---|---|
| `vault:upsert` | `entry` (full entry incl. `id`) | Replace-by-id, or prepend if new |
| `vault:delete` | `id` | Remove entry |
| `vault:replace` | `entries` | Deduplicated full-vault import |
| `delta:approve` | `deltaId` | Apply delta to vault (update in place or unshift-create), remove from queue |
| `delta:discard` | `deltaId` | Remove from queue |
| `delta:approveAll` | — | Apply every pending delta in queue order |
| `delta:discardAll` | — | Empty the queue |
| `delta:queue` | `deltas` | Prepend panel-extracted deltas, cap 100 |

All eight flow through one serialized promise queue (`createMutationQueue` in
`lib/storage-mutations.js`): each task re-reads state, applies a pure
transition, writes, and only then releases the next task. The observer's merge
runs in the same queue, so a panel mutation in flight can never clobber an
observed delta — the lost-update race is structurally impossible.

**Content-script messages** (`action` field, not `type`):

| `action` | From | Effect |
|---|---|---|
| `FORM_SUBMIT_DETECTED` | content script | Observational delta merge into `pendingDeltas` (§6) |
| `UPDATE_BADGE_COUNT` | content script | Set the toolbar badge text |
| `FORM_DETECTED_ON_PAGE` | content script | Per-tab blue badge when ≥3 forms are present |

## 4. Field matching — one rule set (`lib/matcher.js`)

All three contexts share these rules; there are no per-context variants.

1. **`normalizeLabel(s)`** — lowercase, collapse whitespace runs to single
   spaces, trim.
2. **`aliasMatches(query, alias)`** — after normalization:
   - empty on either side → no match;
   - exact equality → match;
   - alias shorter than 8 chars → **no match** (short aliases match exactly
     only, so `"name"` never matches `"Company name"`);
   - otherwise whole-word containment: cached regex `\b<alias>\b` against the
     query (so `"Legal Full Name"` matches a query containing the word
     `"full name"`).
3. **`resolveLabel(el, doc)`** — the label waterfall, in priority order:
   1. `aria-labelledby` target text; 2. `aria-label`; 3. explicit
   `<label for>`; 4. wrapping `<label>` (controls stripped); 5. up to 5
   ancestor levels of container labels/legend/previous sibling (runs **before**
   placeholder so `"Start typing..."` never masks a real label); 6.
   `placeholder`; 7. `name`/`id` fallback, else `"Unnamed Field"`.
   Every candidate passes through `cleanLabelText` (collapse whitespace, trim,
   strip `*:`/whitespace edges, cap 160 chars).

Golden tests (`tests/matcher.test.js`) run the waterfall against committed
fixtures in `tests/fixtures/` — Ashby, Greenhouse, and Lever markup with
`expected-matches.json` — and pin the short-alias and word-boundary cases above.

## 5. Verified-fill contract

A field counts as filled **only when the landed value is proven**. There are no
silent fills.

- `setReactSafeValue` in `content-script.js` returns `{ ok } | { ok: false, reason }`
  for every control kind: inputs/textareas re-read `el.value` after the
  React-safe native setter dispatches input events (`verifyValueLanded` in
  `lib/hydration.js` mirrors the inline check, including the 60-char truncation
  in the failure reason); checkboxes must report the target state (Ashby
  Yes/No pill buttons are clicked and accepted as-is); selects need a matched
  option; radios must report checked after a click.
- The hydrator counts `filledCount` and collects `failedFields`
  (`{ fieldId, query, reason }`); `summarizeHydrationResult` renders it into
  the panel trace. Any unverifiable fill surfaces as a named failure, never a
  success.
- The panel orchestrates fills via injected `chrome.scripting.executeScript`
  calls into the content script's `window.__LOCALFORM_SCAN__`,
  `__LOCALFORM_HYDRATE__`, `__LOCALFORM_SNAPSHOT__`, `__LOCALFORM_AUDIT__`
  hooks (main frame first, then all frames), fills Stage-1 atomic vault fields
  deterministically, and enriches page context with the Chrome Built-in
  Summarizer / LanguageModel when available (`isPlus` path).

## 6. Opt-in observer

Observation is **fail closed**:

1. `content-script.js` checks `observerDomainAllowlist` (via
   `isObserverEnabledForCurrentDomain`): the current hostname must be explicitly
   listed by the user in the panel's Observer tab. Any storage error or missing
   list treats the observer as disabled.
2. Only then, on a submit gesture, it captures a page snapshot and sends
   `FORM_SUBMIT_DETECTED` with the filled fields.
3. The worker's `handleFormSubmitObservation` — running inside the same
   serialized mutation queue as panel mutations — applies the guardrails:
   sensitive-field regex skips (`password`, `ssn`, card numbers, …); dedupe via
   `normalizeForDedup`/`valueAlreadyHeld` (protocol/`www`/punctuation-insensitive
   URL comparisons); never mislabels LinkedIn↔GitHub URLs; never lets a
   company-specific cover letter overwrite the canonical `custom.bio`
   (`Cover Letter Sample (Company)` deltas instead); unmatched values become
   `create` deltas, changed values become `update` deltas against the existing
   entry. Surviving deltas are merged ahead of the queue, capped at 100, and
   the toolbar badge shows the pending count for user review.

## 7. Build, tests, CI

- `npm run build` (`scripts/build.mjs`) validates the manifest and asset
  references, emits `lib/matcher.legacy.js`, and packages `dist/`.
- `npm test` runs vitest + happy-dom over `tests/` (matcher, hydration,
  delta-guards, vault, single-writer incl. the grep guard and the
  interleaved-mutation concurrency test) — 65 tests as of this spec.
- `npm run check` = `test:syntax` (`node --check` on every runtime file incl.
  the emitted twin) + build. Root CI wires the suite as `test:extension`.
- Development is `chrome://extensions` → Load unpacked →
  `chrome-extension/dist`.

## 8. Permissions

Manifest V3 with `sidePanel`, `activeTab`, `scripting`, `storage`; host
permission `<all_urls>` for content-script injection. The scope is deliberately
unchanged this phase (defensible while the extension is unpacked/personal);
reducing it is tracked in `future_work.md`.
